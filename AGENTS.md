# AGENTS.md

FletBox: zero-runtime-dependency vanilla-JS UI framework with a Flet-like declarative API. ESM only (`"type": "module"`), Node >= 20.9. Dev happens on branch `refactory`.

## Commands

- `npm run dev` — `flet-box run --hot`: static dev server on port 8000 with hot reload (`--port` overrides; `--quiet` silences request logs). `flet-box run-spa` is the same server with the SPA fallback (extension-less URLs rewrite to `index.html`).
- Hot reload contract (`bin/commands/runServer.js` + `src/core/hmr-client.js`): chokidar watches the **roots** `src/` and `index.html` and filters by extension in the handlers — chokidar 4 dropped glob support, so `src/**/*.js` is a literal path that never fires. `.css` is hot-swapped by cloning the matching `<link>` with a cache-busting `?t=`; any other change reloads the page **and restores the `useState` RAM**, which `initHMR` snapshots to `sessionStorage` before reloading. Reloads are triggered by the socket, never by a timer: a dropped socket retries once a second and reloads only when the connection *re*-establishes, so a server restart or a tunnel closing an idle socket does not produce an error page or a reload loop. Responses are sent with `Cache-Control: no-store` — a cached module makes a reload look like "nothing detected changes".
- `flet-box cloudflare` (aliases `cf`, `demo`, `tunnel`) — **builds the bundle first, then tunnels `www/`**: `createBundle(target)` → `process.chdir(target)` → `runDevServer({ spaMode: true, hotReload: false })` → `cloudflared tunnel`. It never serves `src/` publicly: `index.html` maps the bare `flet-box` specifier to `./node_modules/...`, so a source-tree tunnel shows a module-resolution error to anyone without that machine's `node_modules`. Two things it depends on that are easy to undo by accident: the SPA fallback injects `<base href="/">` (otherwise a deep link like `/demo/forms/Input` resolves `./loader.js` against `/demo/forms/` and the page comes up blank), and it rewrites `www/config.json`'s `update.url` to `/` (a tunnel is not the Pages origin, so the OTA check was a cross-origin fetch and every visitor's console showed a CORS error). Requires `cloudflared` on PATH; it probes for it *before* building.
- `npm run build` — esbuild-bundles `src/app.js` into `dist/`. Requires `src/app.js` (present at framework root as the demo, so the build works here). Real workflow: `flet-box create <name>` then build inside that project.
- `npm run release -- --patch [--push]` — the ONLY way to bump a version. Requires a clean tree, bumps `package.json` with the odometer scheme (`bin/utils/version.js`: MAJOR unbounded, MINOR/PATCH 0–9 with carry), rebuilds the bundle (`www/config.json` + hash), commits, and tags `vX.Y.Z`. CI publishes that tag to npm; never run `npm publish` by hand. See `docs/guides/online-updates.md`.
- `npm test` — runs static checkers, in order:
  - `node scripts/check-widgets.mjs` — widget-structure contract against `scripts/widget-contract-baseline.json`.
  - `node scripts/check-widget-scale.mjs` — the rem contract, against `scripts/widget-scale-baseline.json` (same shrink-only rule, `--write-baseline` to regenerate). It flags a length written straight to `el.style.*` that is neither `toREM(...)` nor measured geometry, and it fails if `src/widget-factory/` grows a second px→rem converter: `remTool.js` must import `src/utils/units.js`, because the private copy that used to live there divided by a literal 16 and ignored `setBaseFontSize()`, so the same `40` painted 40px through a widget helper and 50px through a routed prop.
  - `node scripts/check-a11y.mjs` — the accessibility contract, with no baseline because every rule is absolute: nothing in `src/` writes an inline `outline` (it outranks the engine's ring — that is how a focused field came to have none) and the registry routes no `outline` prop; `src/utils/focusRing.js` still holds the `:focus-visible` rule, the `--color-focusRing` token and the `[data-fb-field]` `:has()` pair, injected once from `createWidget.js`; both palettes define `focusRing` and the rule's boot fallback equals the boot palette; `effects.js` still gives a pressable widget role, Tab stop, Enter/Space and a released keydown listener, and does it outside the `disableTransform` branch; every file that reads the Escape key also imports and releases `trapFocus`; the trap's `FOCUSABLE_SELECTOR` and the ring's selector are the same list; no widget or navigation assigns `el.onclick` after the factory returned unless the same file passes it to `applyEffects` (the Dropdown's listbox option is the one allowlisted exception, and a stale entry fails too); and `Input` still writes the field marker. Proven by 19 mutations, one per guard.
  - `node scripts/check-prop-registry.mjs` — the `ALL_PROPS` registry vs what widgets/navigations actually read.
  - `node scripts/check-docs-props.mjs` — the `docs/widget/*.md` prop tables vs the registry, the implementations and `src/index.d.ts`. Blocks `DEAD` (a documented prop nothing routes or reads) and `BOOL_STYLE` (a documented `boolean` that reaches CSS as `1` because its registry entry has no `boolValues`).
  - `node scripts/check-api-surface.mjs` — API coupling across the three surfaces. It imports `src/index.js` for real, so it also fails when the barrel re-exports a name that no longer exists, or when the package stops being importable in Node (module-scope `window`/`document`).
  - `node scripts/check-router-base.mjs` — deployment base path.
  - `node scripts/check-cli-install.mjs` — the shape of the **published** package: it `npm pack`s the repo, extracts the tarball and runs `bin/cli.js` from it with no `node_modules` in scope, which is the only place where a `bin/` module reaching for a devDependency at import time shows up (it used to break every CLI command for consumers, since the checkout always has `ws`/`chokidar`). It also asserts `docs/widget/` shipped.
  - `node scripts/check-clean-ui.mjs` — the contract for `flet-box check-ui`: the screen the design skill recommends must produce **no** finding, and every tier must be proven to bite by breaking it. Its last section asserts the two themes expose the same token names — the light palette once answered five fewer tints than the dark one and the boot palette, so `setTheme("light")` deleted `colors.errorBg` & friends out from under an app that was already writing them.
  - `node scripts/check-framework-ui.mjs` — the same gate, run on this repo's `src/`: `npm test` fails when a default the framework ships breaks a rule it teaches. `scripts/framework-ui-baseline.json` is shrink-only and every entry carries its reason; `--write-baseline` exits 1 while an entry has no justification, so a new finding is fixed rather than snapshotted.
  - `node scripts/check-skills.mjs` — the `skills/` folder contract (see Skills below): each file loads, every API it teaches is real (fenced blocks through `checkApi`, inline `Widget({ prop: … })` through `bin/utils/dtsProps.js`, every `colors.X` against **both** palettes, every effect against `AnimatedBox`, every rule number against the codes `checkUi` reports), the folder is in the tarball, and a freshly created app gets byte-identical copies in all three loader roots with every markdown link resolving. Both halves are mutation-tested: an invented prop and a pointer at nothing must fail the script.
  - `python3 tools/snippets-creator-flet-box/build_snippets.py --check` + `node scripts/check-snippets.mjs` — the VSCode snippet library (see Snippets below).
  Behavioral tests are browser harnesses in `tests/` (below).
- `python3 scripts/generate_widget_docs.py` — regenerates `docs/widget/*.md` from `src/index.d.ts` + the curated examples in `scripts/_docdata/`. Run after changing a widget's public props/types. Prop blurbs live in the flat `DESC` map, which is keyed by prop name **alone** — adding `markers` there for one widget rewrites every page that documents a `markers` prop. When a name already means something else elsewhere (`markers` = pins on a map, ticks on an arc), put the blurb in `WIDGET_DESC[Widget][prop]` instead.
- Snippets: the dictionaries in `tools/snippets-creator-flet-box/FletBox_snippets_creator/` are the ONLY source. The four JSON files beside them (including the aggregate `FletBox.json`, which is what the editor loads) are build output — never hand-edit them, run `python3 tools/snippets-creator-flet-box/build_snippets.py`. Prefixes must stay unique across the three dictionaries: one prefix, one snippet, or the aggregate silently keeps the first file's version.
- `flet-box build android [--release [--aab]]` / `flet-box build ios [--archive]` — Capacitor builds, run **inside a generated project**. Both share `bin/utils/capacitor.js`; each owns its toolchain checks (`buildAndroid.js`: SDK + JDK; `buildIOS.js`: full Xcode + CocoaPods + simulator runtimes). Android `--release` leaves the artifact **unsigned on purpose** so it can be signed with the developer's own keystore (`apksigner` for the APK, `jarsigner`/Play App Signing for the AAB).
- `flet-box run-native <android|ios> [--device|--livereload]` — wraps `npx cap run` to compile and launch on an emulator/simulator or device. It reuses the toolchain helpers exported by `buildAndroid.js` (`prepareAndroidEnvironment`) and `buildIOS.js` (`requireAppleToolchain`); keep those exports when editing the build commands.
- No lint/formatter/typecheck config exists. Validate JS with `node --check <file>` and `python3 -m py_compile scripts/generate_widget_docs.py`.
- `flet-box audit-fix` (aliases `fix-imports`, `fix-path-imports`, `auditFix`) is the *repair* half of that gate: it rewrites what `check-api` can prove — a wrong relative path, a default import of a named-only widget, a missing `import` line for a bare identifier (merged into the existing flet-box import when there is one), and a mistyped prop key — and prints everything ambiguous under "Left for you to decide" untouched. `--only imports|props`, `--root <dir>`. It writes files directly, so the rule is strict: rewrite only when **exactly one** candidate is within a length-gated edit distance (`strictMatch` in `bin/commands/auditFix.js`: 0 for names < 4 chars, 1 up to 8, 2 from 9) and a tie means no edit. Prop keys are only touched when the identifier is a known flet-box import and the key is in neither `PROP_MAP` nor `STRUCTURAL_PROPS`. `flet-box create` wires it as `npm run fix`. Reuses `loadApi`/`nearest`/`collectSources`/`STRUCTURAL_PROPS` exported from `checkApi.js` — keep those exports.
- `flet-box check-api` (alias `flet-box check`) is the anti-hallucination gate: it imports `src/index.js` and reads `translateProps.js` + `src/index.d.ts` of the resolved package and reports invented widgets/props, positional widget calls, foreign-framework imports and broken imports between the app's own modules (`MODULE_NOT_FOUND`, `MISSING_EXPORT` — a name the target file never exports, resolved statically so it works offline and in CI). `--props <Widget>`, `--list`, `--emit-api`, `--json`, `--root <dir>`. Errors exit 1. `flet-box create` wires it into every app as `npm run check` (plus `AGENTS.md`, `.claude/CLAUDE.md`, `.cursor/rules/fletbox.mdc`, `.fletbox/memory/` and `.fletbox/api/cheatsheet.md`), and CI runs it — so a template that uses a non-existent export or prop fails the generated app immediately.
- `flet-box unpack <Widget>` (`bin/commands/unpack.js`) is the *read* half: it cross-checks the four places a prop lives — `src/index.d.ts`, the `ALL_PROPS` registry, the widget's own source, its doc page — and labels every disagreement `DEAD` (typed, routed by nothing, read by nothing), `INVENTED` (read by the widget, declared nowhere), `UNDOCUMENTED` (the engine routes it, the interface hides it), `DOC-ONLY`, `CODE-ONLY`. Flags: `--example` (a paste-ready call built only from verified props, and it never drops a required one), `--diff`, `--all`, `--json`, `--md`, `--root <dir>`. `unpack --all` writes `.fletbox/api/api.json` + `api.md`; `flet-box create` generates them at scaffold time and wires `npm run api` to regenerate. Two invariants to keep: the widget filter is `exported && propsSource()` (a singleton API like `initRouter` has no props interface and must not appear), and `readProps()` reads structure from the **neutralised** source (`bin/utils/neutralise.js`) while slicing values out of the raw text at the same offsets — splitting a destructuring pattern on raw commas invents props, which is exactly how `Consolas/Menlo/Monaco` became props of `Markdown`. Shared parsing lives in `bin/utils/dtsProps.js` (`parseSignatures`, `membersOf`, `resolveInterfaceProps`) and is reused by `check-api`; keep those exports and `loadApi`/`nearest`/`STRUCTURAL_PROPS` in `checkApi.js`.
- `flet-box to-png [dir]` (aliases `topng`, `convert-images`; `bin/commands/toPng.js` + `bin/utils/images/`) converts a folder of asset images to PNG with **Node core only** — no `sharp`, no CLI binary. The decoders are the point: JPEG (baseline + extended sequential, grey/RGB, any sampling factor, restart intervals), PNG (colour types 0/2/3/4/6, 1–16 bit, all five row filters, `tRNS`), BMP (uncompressed 1/4/8/24/32) and GIF (first frame, interlace, transparency). Progressive JPEG, Adam7 PNG, RLE BMP, WebP, AVIF, TIFF, ICO and SVG are **declined by name**, never guessed. Format comes from the bytes, so a `.jpg` that is really a PNG is read as a PNG — keep it that way. The writer is the other half: `encodePng` picks the layout from the pixels it is handed (an exact palette when there really are ≤256 distinct colours, grey when the channels already agree, three bytes per pixel when no pixel uses alpha) and picks row filters by deflating the candidates at level 9 and keeping the shortest IDAT, so the output is the smallest **lossless** PNG it can find — nothing quantises a pixel, and `FULL_SEARCH_LIMIT` is what stops a 2738² photo from searching six deflates per layout. It is non-destructive: the source stays, `logo.png` is written beside it, and an existing `logo.png` is reported as a name clash instead of overwriting a hand-made asset (`--force` opts in); `--replace` deletes a source only after the written PNG has been read back (`writtenPngMatches`). `--optimize` re-packs files that already are PNG and replaces one only when the new bytes are smaller **and** `pngHoldsThePicture` reads them back equal, through a temp file plus a rename; a 16-bit PNG is left alone, because narrowing it is losing quality for a byte count. A photograph's PNG is 3–4× its JPEG and that is the format speaking — the command converts anyway and prints the ratio, so do not "fix" it by refusing. Flags: `--out --replace --force --optimize --flat --dry-run --quiet`; the summary counts converted / declined / already png / optimized / already optimal / name clash and the bytes saved, and only an undecodable file counts as a failure (exit 1). Contract: `node scripts/check-image-convert.mjs` (standalone for now — it is **not** in `npm test` yet) compares the decoders against `tests/fixtures/images.json`, whose expected pixels come from another decoder, not this repo's: lossless formats must match byte for byte, JPEG is measured against libjpeg's own pixels (mean ≤ 0.33, worst channel 2 — the line printed per fixture is the regression signal). The optimizer asserts on the same fixtures: never bigger than the plain type-6/None writer, never type 6 for an opaque frame, never a palette over 256 colours, and `every layout is reached` (types 0/2/3/6) so a branch cannot go untested because no fixture hits it — `png-gradient` (1024 colours) exists for exactly that. Every one of those guards has been proven to bite by mutating the rule in a scratch copy; a new one needs the same, and note that a mutation only counts if it changes the layout the picker *selects* (a size-neutral corruption), or the search silently routes around it. Regenerate fixtures with `python3 scripts/generate-image-fixtures.py`, which needs **Pillow and is dev-only** — like `tests/` itself it sits outside `package.json` `files`, so neither the generator nor the fixtures reach a consumer. `scripts/check-cli-install.mjs` is what proves the whole thing survives `npm pack`: no `bin/` image module may import anything outside `node:*`.

- `flet-box images [dir]` (aliases `optimize-images`, `imgs`; `bin/commands/images.js` + `bin/utils/imageTools.js`) is the **lossy** half, and it delegates: a photograph has no answer inside `dependencies: {}`, so the command finds the platform's own encoder (`cwebp`, then `magick`, then `convert`), probes it with `--version` rather than `which`, and shells out to it — the same shape as `runCloudflare.js` requiring `cloudflared` and `buildAndroid.js` requiring the SDK. A binary is not an npm dependency and no `bin/` module here imports anything outside `node:*`, which is what `check-cli-install.mjs` keeps proving. When nothing is installed it prints the one command for that machine (`platformInstaller()` reads `process.platform`, and on Linux the family from `/etc/os-release`, because apt/dnf/pacman are different sentences); `--install` runs it, and only on a TTY — a CI runner must not find a CLI reaching for `sudo`. The search order is the contract: pixels first, quality second (`WIDTH_SCALES` then the quality ladder down to `QUALITY_FLOOR = 62`), because a soft 540px q70 photo beats a blocky q44 one and nothing on a page renders the pixels a 2000px sensor captured. Non-destructive like `to-png`: the WebP is written beside the source, an existing one is a name clash unless `--force`, a WebP already inside the budget is **not** re-encoded (a second lossy pass on bytes the same encoder already chose buys nothing), and `--replace` deletes a master only after the output's 12 header bytes sniff as `RIFF…WEBP` — there is no WebP decoder here, so that is the honest read-back. Flags: `--budget <KB>` (40), `--width <px>`, `--quality <n>`, `--force --replace --install --dry-run --quiet`; only an encoder that produced nothing counts as a failure (exit 1), and a file that cannot fit the budget is still written at its smallest attempt and printed `OVER`.
- `flet-box prune-assets [dir]` (alias `prune`; `bin/commands/pruneAssets.js`) deletes the images a generated app never names, because `flet-box create` ships a demo library (dishes, drinks, gallery) that no screen imports and that any broad asset glob drags into a release. A file is referenced when its path **or** its exact filename appears in `src/`, `index.html`, `scripts/`, `fletbox.config.json`, `package.json`, `README.md`, `AGENTS.md` — with comments stripped first (`mojito.jpg is the frappé` is documentation, not a load) and `www/` excluded, since a name that only appears in generated output is a stale bundle, not a consumer. `assets/logo.png` is protected by rule: the native icon and splash scripts build that path at runtime, so a text scan cannot see its consumer. Dry run by default, `--apply` deletes, `--keep <name>` adds a protection, and it refuses a folder outside `--root`. The asset dir resolves against `--root`, never against the shell's cwd — that disagreement is exactly what the first draft of `scripts/check-images-cli.mjs` caught.
- `node scripts/check-images-cli.mjs` is the contract for both (standalone, like `check-image-convert.mjs`: it needs a binary that may not exist). Its fixtures are **synthetic**, written by the repo's own `encodePng`, so no Pillow and no committed bytes are involved.
- `images --referenced` publishes only what the app actually loads, and it is stricter than "the name appears somewhere": a WebP is written when the app names **the WebP**, never because it names the source it would replace. That is what kept `favicon.png` — a format the browser must be handed as PNG — from being converted into a file no consumer asks for. `--replace` refuses to delete a master the app still names in its own extension (`source kept: the app names X.png, not X.webp`).
- Alpha is verified from the written bytes, not from the encoder's exit code. `hasTransparency()` reads the decoded source, `webpCarriesAlpha()` reads the RIFF chunks back (`ALPH`, then the `VP8X` flag bit, then the `VP8L` packed word), and a WebP that lost the transparency is deleted and the file printed as failed. A lossy encoder quietly dropping a transparent margin is exactly what "the icon turned white on every home screen" would have been, and the negative control in `check-images-cli.mjs` asserts an opaque source is reported opaque, so the guard cannot pass by always saying "alpha".
- `decodeImage` declines WebP and progressive JPEG; `readImageHeader()` still reads **size and alpha presence** from those headers (`SOF` markers, `0xC4`/`0xC8` skipped, `0xC2` noted as progressive). An `UnsupportedImage` is therefore not a dead end for `images`: the encoder reads the file itself, the header only picks the scale ladder. It is what let `og-cover.jpg` be shrunk instead of skipped.
- `createBundle` stamps the social preview card: `absoluteShareTags()` (`bin/utils/bundleConfig.js`) rewrites `og:image`, `og:image:url`, `og:url`, `twitter:image`, `twitter:url` to absolute URLs from the OTA origin, and `www/index.html` is the only file it touches. It prefixes values with no scheme, so it is idempotent, and leaves every other meta alone. A share scraper crawls from `https://`, not from the repo's `<base>`: without this the link preview shows no picture at all, even though the page itself is fine. Guarded by `check-ota-assets.mjs`.
- A Pages deployment is built from the **published npm package**, not this checkout, so what `createBundle` copies on this machine is not proof of what CI publishes. `githubWorkflow()` is the only workflow shape a generated app gets (`concurrency: group pages / cancel-in-progress: false`, `actions/configure-pages@v5` in the build job, `upload-pages-artifact` with `path: www`, `deploy` needing `build`) and `check-router-base.mjs` asserts that shape over the generated text — a `tags:` key that drifts out from under `push:` makes the whole file unparseable, and GitHub then reports a failed run with no job and no step to read.

- The generated app's agent contract is `templates.agentsMd()` in `bin/utils/templates.js`, mirrored by `claudeMd()` and `cursorRules()` — all three are arrays of single-quoted lines joined with `\n`, so an apostrophe inside a line must be escaped or the template stops compiling. Its numbered sections are load-bearing and cross-referenced by number ("the design system in section 4", "the checker in section 5"): inserting or removing a section means renumbering the rest and that prose. §4 is the design system (one brand color per screen from the `colors` tokens, no hex literals; spacing/radius/type only from the 8-based scale 4·8·12·16·18·24·32·48) and every token name in it was read off the real `colors` export — do not "tidy" one into a name that does not exist.
- `flet-box create <name> --template <basic|adaptive|blank|full|sidebar>` (and `--template=<name>`) is equivalent to the `--blank`-style flags. The **first** positional is always the project name; a later one is treated as an unclaimed flag value and is ignored, because a value that leaked past the parser used to rename the project (`create myapp --template blank` built a folder called `blank`).

## Skills

`skills/` at the repo root is the framework's knowledge of how to build and design
a FletBox app, written as four real markdown files — one per subject, not one per
idea:

- `fletbox-rules` — the working contract: FletBox syntax only, never invent an
  API (and the four ways to look one up), the rem rule, aliases, cleanup, the two
  gates, the memory duty.
- `fletbox-design` — the numbered design rules (00…24). Every code `flet-box
  check-ui` reports maps to one of them, and `docs/guides/clean-ui.md` keeps the
  code→rule table, so renumbering a rule means editing that table in the same
  change; `scripts/check-skills.mjs` already fails if a code the gate emits is not
  named by the skill.
- `fletbox-motion` — whether a thing may move, and through which of `AnimatedBox`,
  `AnimatedText`, `ParallaxBox` or `animate`.
- `fletbox-memory` — the `.fletbox/memory/` journal that hands progress from one
  AI to the next, including `notes/current-status.md`.

`bin/utils/skills.js` reads them (`skillRoot`/`skillNames`/`readSkill`/
`readFrontmatter`) and `flet-box create` **copies the bytes** into the app at
`skills/`, `.claude/skills/<name>/` and `.qoder/skills/<name>/` — the last two are
where those assistants load a skill from, so they are mirrors, never the source —
plus a `.cursor/rules/<name>.mdc` pointer per skill (`templates.skillCursorRule`;
`fletbox-rules` and `fletbox-design` are `alwaysApply: true`, the other two fire on
their subject). Keep `package.json` `files` carrying `skills/` or an installed app
has no design contract at all. `scripts/check-skills.mjs` proves the whole chain.

Do not add a fifth skill for one new idea — extend the file that owns the subject,
and move anything the four already cover out of `templates.js` prose. The set is
four on purpose: an agent that is sent to nine files reads none.

## Generated mobile projects

`flet-box create` writes the Capacitor scaffolding: `capacitor.config.json`, `assets/logo.png`, and one asset script per platform (`scripts/sync-android-icons.mjs`, `scripts/sync-ios-assets.mjs`) wired into the `android:sync` / `ios:sync` npm scripts. Every template is a string in `bin/utils/templates.js` **except** the skills, which are files in `skills/` precisely so the prose has one copy.

Quirks that are easy to break when editing those templates:

- A template literal cannot contain unescaped inner backticks in the generated file. Inside a generated template literal, a nested backtick must be `\\\`` (emits ``\` ``), and a nested `${` must be `\\${`. When in doubt, generate the project and `node --check` the output.
- The iOS asset script reads icon/launch slots from `ios/App/App/Assets.xcassets/*/Contents.json` instead of hardcoding file names, because Capacitor owns those names and can change them between major versions.
- The iOS app icon must be flattened onto an opaque background: App Store validation rejects icons with an alpha channel.
- `LaunchScreen.storyboard` lays the splash image out inside the safe area, so its background color must match the launch image or the notch strip flashes white.


## Testing

Tests are dependency-free JS in `tests/`. They can be run headlessly with `npm run test:browser` (`scripts/run-browser-tests.mjs`: serves the repo, drives the system Chrome through puppeteer, and reads each harness's global). That script is optional — it resolves puppeteer from `$FLETBOX_PUPPETEER` or a sibling checkout and a browser from `$FLETBOX_CHROME` or the usual install paths, and skips with a notice when either is missing, so it never breaks `npm test`. To run one harness interactively: `npm run dev`, then open:

- `/tests/index.html` — widget-factory regression contract. Treats the factory as frozen: fixes belong in widgets, not `src/widget-factory/`.
- `/tests/smoke.html` — instantiates every widget to catch `ReferenceError`s.
- `/tests/motion.html` — the motion contract: the named transitions actually move the element (`translateX/Y`/`rotate`/`scale` merge into one `transform`), every `EASING_NAMES` curve starts at 0 and ends at 1, a spring settles, and reduced motion (`setMotionMode('reduce')`) collapses every loop to one frame that writes the end value.
- `/tests/a11y.html` — the accessibility contract: a focused control paints the engine's ring (2px at 2px offset in `--color-focusRing`, and the harness re-registers that token to prove the ring reads it), `outline: none` appears on no element, a pressable `Container`/card answers Enter and Space, an icon wired after construction is a named control while a decorative one stays `aria-hidden` and off the Tab path, the three overlays trap the keyboard and give it back on close, and an invalid `Input` is `aria-invalid` with a live description that clears when the value becomes valid.
- `/tests/regression.html` — guards for the bugs fixed in the widget audit (engine child-wipe, `ListView.updateData`, `DataTable` body rebuild, `SnackBar.close` idempotency, `AnimatedBox` keyframe dedupe, `MatrixRain` loop teardown). Add an assertion here for every bug you fix: each one failed before its fix.
- `/tests/doccheck.html` and `/tests/doccheck-all.html` — assert documented behavior on the real runtime.
- `/tests/propscan.html` — prop scanner.
- `/tests/maps-chile.html` — manual Maps debug page: one map of Chile, no markers, with an on-page log of tiles loaded and the last `onMoveEnd`. Not an automated harness (no pass/fail globals); drive it with `window.__MAPS_DEBUG` (`{ map, stats, say }`).

Each harness writes a global (`window.__TESTS`, `window.__SMOKE`, `window.__REGRESSION`, `window.__DOCCHECK`, `window.__CONTRACT`, `window.__MOTION`, `window.__A11Y`) for automation. These pages cannot open via `file://` (ESM + CORS); they must be served.

## Architecture

- Public entry `src/index.js`; types in `src/index.d.ts`. A public API is complete only when three surfaces agree: runtime implementation, `src/index.js` export, and `src/index.d.ts` declaration — `scripts/check-api-surface.mjs` enforces this under `npm test`. Two rules follow from it: every `interface`/`type` in `index.d.ts` must be `export`ed (otherwise consumers cannot `import type` it), and the package must stay importable in Node (never touch `window`/`document` at module scope — guard with `typeof window !== "undefined"`).
- `src/widget-factory/` is the ONLY rendering engine — `WidgetFactory` turns props into an `HTMLElement` with style, events, children, lifecycle, and reactivity. Never add a second rendering system.
- `src/create-index.sh` is STALE: it writes to a non-existent `src/widget-builder/`. Do not run it.
- Adding a widget: file in `src/widgets/`, export from `src/widgets/index.js` and `src/index.js`, type + props in `src/index.d.ts`, doc page + `basic`/`normal`/`full` examples in `docs/widget/`.
- Prop aliases are a deliberate feature (e.g. `bgColor` ≡ `backgroundColor`, `onPress` ≡ `onClick`), resolved by the factory; each alias must keep exactly one meaning. Widgets also expose reactive property setters (e.g. `widget.text = ...`).
- State is key-based RAM + subscribers (`useState`); router lives in `src/navigations/Router.js`.
- Every length is a framework unit, not a pixel: a number on a rem-routed prop becomes `value / BASE_FONT_SIZE` rem, so the whole UI grows with the reader's browser font (that is what makes one build fit phone, tablet and desktop). `toREM` also rewrites a hand-written pixel shorthand — `"8px 12px"` → `"0.5rem 0.75rem"` — while anything that is not made only of pixel tokens (`"50%"`, `"calc(100% - 8px)"`, `"2px solid red"`) passes through untouched. Pixels stay where pixels are honest: canvas backing stores (QRCode, Chart, CircularBar, CircularChart), Maps' projected tile/pin space, values measured from the DOM (`offsetWidth`, `getBoundingClientRect`, scroll offsets), the hairline `borderWidth`, `SHADOW_LEVELS` depth, the focus ring's `2px` outline and `2px` offset (a visibility constant, not a length the layout scales — a rem would shrink it under the threshold that makes it visible), and a virtualised row's px-space math — `ListView` converts `itemSize + gap` through the live root font size so the slot a row gets scales the way the row's own box does. The design numbers defaults are drawn from live in `src/tools/scale.js`, which `bin/commands/checkUi.js` re-exports so the app gate and the widgets cannot disagree.
- Widgets that register resources must clean them up: window/document listeners, timers/RAF, observers, router/storage subscriptions.
- Reduced motion is decided once, in the engine (`src/animations/motion.js`). `prefersReducedMotion()` is read by the imperative loop (`motionDuration()` collapses a run to one frame that writes the end value), by `AnimatedBox`, `ParallaxBox`, `MatrixRain` and `applyPulse`. Anything that ends up with an `infinite` CSS animation must carry the `data-fb-anim` hook so the once-injected `@media (prefers-reduced-motion: reduce)` rule reaches it: the factory's `setStyles` marks every `animation`/`animationIterationCount` write (that is what covers `Skeleton`'s wave and any app prop), and a widget that writes `el.style.animation` directly calls `markMotionLoop(el)` itself.
- Accessibility follows the same shape: decided once in the engine, never re-derived per widget. The focus ring is one `<style id="fletbox-focus-ring">` injected by `ensureFocusRing()` from `src/utils/focusRing.js`, called once in `createWidget.js`; it paints `:focus-visible` in `var(--color-focusRing, …)`, so a theme moves the ring with everything else. Nothing inside `src/` may write an inline `outline` — an inline value outranks the stylesheet and silently deletes the ring everywhere (`scripts/check-a11y.mjs` fails on the first one). The ring sits at `2px`/`2px` offset outside the border, so the border keeps reporting validation and the ring reports focus; a widget whose visual control is a wrapper around a native input marks that wrapper `data-fb-field` and the stylesheet rings the whole box instead of a hairline inside it. A press handler must arrive as a prop (`onClick`/`onPress`) at construction: `applyEffects` runs `makeKeyboardPressable`, which gives the element `role="button"` (only if it has none), `tabIndex=0`, Enter/Space, and releases its listener on unmount. Assigning `el.onclick` after the factory returned is mouse-only and caught by `check-a11y`'s `late-onclick` rule (the `Dropdown` listbox option is the one allowlisted case). The three overlays (`Modal`, `Drawer`, `BottomSheet`) hold the keyboard through `trapFocus` from `src/utils/focusScope.js` and release it on close, which returns focus to whatever opened them.

## Repo layout gotchas

- The backend is a separate package and repo, `flet-box-server` (a sibling checkout, `../flet-box-server`); `docs/server/` documents it from here. It is NOT part of this repo and is not published with the framework — don't wire it in, and don't import it from `src/`.
- `www/` and `dist/` are gitignored build output — regenerate them with `npm run build` or `flet-box release`, never hand-edit them. `www/` is built from the root demo (`src/app.js` + `index.html`) so `flet-box run-bundle` works here; in a generated app it is the OTA source that CI publishes to Pages — `build.yml` deploys every push (so the preview is never stale) but deletes `www/config.json` unless the ref is a `v*` tag, which is what keeps installed apps on the last release, and Android/iOS only run from `build-native.yml` when started by hand — and it stays out of git there too.
- `.github/workflows/npm-publish.yml` is the only workflow: it publishes to npm when `package.json` carries a version npm doesn't have yet. APK/AAB CI belongs to generated apps (`bin/utils/templates.js` writes theirs), not here. No CI runs the tests.
- npm ships all of `bin/`, so a stray `bin/package.json` would be published and shadow module resolution. Keep `bin/` free of package manifests.
- `bin/` may not import a devDependency at module scope. `ws` and `chokidar` exist only for the dev server, so `bin/cli.js` loads `runServer.js`/`runBundle.js`/`runCloudflare.js` with `await import()` inside their command branches; keep them lazy or `flet-box` crashes on every command for anyone who installs it from npm. `check-cli-install.mjs` (above) is the tripwire.

## Widget structure contract

Every widget follows the canonical, modular shape documented in
[`docs/guides/widget-structure.md`](docs/guides/widget-structure.md); `QRCode.js`
is the reference implementation. In short: one `WidgetFactory` root, `widgetName`
on that root, `composeUpdate()` instead of overwriting `container.update`, scoped
styles, and every resource released through an idempotent `onUnmount` disposer
(never `_cleanup` monkey-patching).

`npm test` enforces this statically via `scripts/check-widgets.mjs`; the debt
snapshot lives in `scripts/widget-contract-baseline.json` and must only shrink.
Before marking a widget done, also open `/tests/widget-contract.html` (runtime
contract) and `/tests/smoke.html` (every widget instantiates).
