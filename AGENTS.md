# AGENTS.md

FletBox: zero-runtime-dependency vanilla-JS UI framework with a Flet-like declarative API. ESM only (`"type": "module"`), Node >= 20.9. Dev happens on branch `refactory`.

> **This document is for maintaining the framework.** If you are *generating an app*
> with FletBox, read [AGENTS_FOR_CODE_GEN.md](AGENTS_FOR_CODE_GEN.md) instead — it
> is the contract for writing code against the framework: the golden rule (a prop
> that is not in the cheatsheet does not exist), the prohibitions, the ten design
> rules that survive a review, what gets rejected, and the verification protocol.
> It ships inside every app `flet-box create` builds.

[CONTRIBUTING.md](CONTRIBUTING.md) is the same contract for a human: the map of
the repository, the gates and what each one proves, the commit conventions, and
the rule that every one of them is proven twice — once by breaking it, once by
obeying it.

## Commands

- `npm run dev` — `flet-box run --hot`: static dev server on port 8000 with hot reload (`--port` overrides; `--quiet` silences request logs). `flet-box run-spa` is the same server with the SPA fallback (extension-less URLs rewrite to `index.html`).
- Hot reload contract (`bin/commands/runServer.js` + `src/core/hmr-client.js`): chokidar watches the **roots** `src/` and `index.html` and filters by extension in the handlers — chokidar 4 dropped glob support, so `src/**/*.js` is a literal path that never fires. `.css` is hot-swapped by cloning the matching `<link>` with a cache-busting `?t=`; any other change reloads the page **and restores the `useState` RAM**, which `initHMR` snapshots to `sessionStorage` before reloading. Reloads are triggered by the socket, never by a timer: a dropped socket retries once a second and reloads only when the connection *re*-establishes, so a server restart or a tunnel closing an idle socket does not produce an error page or a reload loop. Responses are sent with `Cache-Control: no-store` — a cached module makes a reload look like "nothing detected changes".
- `flet-box cloudflare` (aliases `cf`, `demo`, `tunnel`) — **builds the bundle first, then tunnels `www/`**: `createBundle(target)` → `process.chdir(target)` → `runDevServer({ spaMode: true, hotReload: false })` → `cloudflared tunnel`. It never serves `src/` publicly: `index.html` maps the bare `flet-box` specifier to `./node_modules/...`, so a source-tree tunnel shows a module-resolution error to anyone without that machine's `node_modules`. Two things it depends on that are easy to undo by accident: the SPA fallback injects `<base href="/">` (otherwise a deep link like `/demo/forms/Input` resolves `./loader.js` against `/demo/forms/` and the page comes up blank), and it rewrites `www/config.json`'s `update.url` to `/` (a tunnel is not the Pages origin, so the OTA check was a cross-origin fetch and every visitor's console showed a CORS error). Requires `cloudflared` on PATH; it probes for it *before* building.
- `npm run build` — esbuild-bundles `src/app.js` into `dist/`. Requires `src/app.js` (present at framework root as the demo, so the build works here). Real workflow: `flet-box create <name>` then build inside that project.
- `npm run verify` (= `flet-box verify`, `bin/commands/verify.js`) — the **one command**: it parses every module, runs the anti-hallucination check, the clean-UI check, the structural check and the prop contract, and then runs the project's own suites — one report, one exit code. The parse gate (`bin/commands/checkSyntax.js`) hands every `.mjs`/`.cjs`/`.js` outside `node_modules`, `www` and `dist` to `node --check`, the parser the runtime uses, and reports `file:line:column`, the offending source line with a caret under the character and a hint drawn from the message; without it a missing `)` passed all four text gates as "the code is legal" and the app came up blank in the browser. Hidden folders are walked, because a script under `.qoder/skills` or `.claude/skills` is code the project runs — only the VCS database and the vendor caches (`.git`, `.yarn`, `.cache`, …) are skipped, so `.qoder/skills` is inside the gate that exists to parse it. The suite gate runs whichever of `test`, `test:browser` and `test:visual` the project's `package.json` declares, one after another, with `--silent` so npm's own error block cannot bury the line the failing check wrote; a project that declares none (a generated app) gets a skipped step, not a green one. The suites are the slow half (~59 s here), so `--watch` and `run --verify` leave them out and `--only tests` runs them alone; a `test` script that calls `verify` cannot recurse (`FLETBOX_VERIFY_NESTED`), and a caller that runs the suites elsewhere — the CI gates job — says so with `--no-tests`, which drops the gate instead of pretending to be a nested run. `scripts/check-syntax.mjs` proves that a failing suite cannot decide the exit code of a `--no-tests` run. Every finding prints its `file:line:column`, the code, the message and a `→` suggestion, warnings included — a warning used to be counted and never named (`ui 2 warning(s)` with no line), which is the one thing an agent cannot act on; past 12 of them the report points at `--json`. The design gate reads `scripts/framework-ui-baseline.json` **in the framework checkout only** (`isFrameworkProject`), so the two findings this repo has already decided about are counted as `2 accepted` instead of being re-printed under "what to review" on every run; a consumer's app has no baseline to appeal to and keeps every finding. An accepted finding no longer fails the run, whatever its code — that is what its written reason is for — which `scripts/check-clean-ui.mjs` proves in both directions. `flet-box verify --fix` runs `audit-fix` first so a typo is repaired by the tool that can prove the repair; `--watch` re-runs it on every edit (500 ms debounce) and `flet-box run --verify` does the same while the dev server runs. It lives in `bin/` because it ships inside every app `flet-box create` builds, and it may not reach for a devDependency there. The prop contract it reads comes from `unpack`'s `unpackWidget`/`propsSource`/`definitionIndex` — keep those exports. The structural gate (`bin/commands/checkStructure.js`) owns only what no other gate owns — a cycle between two of the app's own modules, a module outside the project's folders, markup written by hand — and it treats the framework itself as package code, because the framework *is* the rendering engine.
- `npm run metrics` (= `flet-box metrics`, `bin/commands/metrics.js`) — reads the **metrics log**: every `flet-box verify` run appends a row to `metrics/generations.md` (a generated app keeps it in `.fletbox/metrics/generations.md`), green or not, because a log of only successes cannot tell a correction from a first try. A *generation* is a run of failing rows closed by the first green one, and the **north metric** is the share of generations whose first run was green — the share of code that passed the gate with no correction at all. The command also prints the three failures that recur most often and the rule each one should belong to, and it **fails** when a code has come back three times with no rule behind it: that is the loop closing. `scripts/check-metrics.mjs` is its contract test.
- `npm run release -- --patch [--push]` — the ONLY way to bump a version. Requires a clean tree, bumps `package.json` with the odometer scheme (`bin/utils/version.js`: MAJOR unbounded, MINOR/PATCH 0–9 with carry), rebuilds the bundle (`www/config.json` + hash), commits, and tags `vX.Y.Z`. CI publishes that tag to npm; never run `npm publish` by hand. See `docs/guides/online-updates.md`.
- `npm test` — runs static checkers, in order:
  - `node scripts/check-widgets.mjs` — widget-structure contract against `scripts/widget-contract-baseline.json`.
  - `node scripts/check-widget-scale.mjs` — the rem contract, against `scripts/widget-scale-baseline.json` (same shrink-only rule, `--write-baseline` to regenerate). It flags a length written straight to `el.style.*` that is neither `toREM(...)` nor measured geometry, and it fails if `src/widget-factory/` grows a second px→rem converter: `remTool.js` must import `src/utils/units.js`, because the private copy that used to live there divided by a literal 16 and ignored `setBaseFontSize()`, so the same `40` painted 40px through a widget helper and 50px through a routed prop.
  - `node scripts/check-shared-helpers.mjs` — one home per shared helper, because copies do not diverge when they are written, they diverge when one of them is fixed. `src/helpers/` is that home: one file per behaviour and **no imports at all**, which is what makes the module safe to import from anywhere. It fails on a second definition of `injectKeyframes` or of the HTML escaper, a second stable keyframe hash, a second copy of the four-side box cascade, an `@keyframes` rule written outside `src/utils/styleInjector.js`, or a helper that imports another module (that one is a service and belongs in `utils/`). It also asserts the modules that used to carry a copy still import the home. `--root <dir>` checks another checkout, which is how each rule was proven to bite (six mutations, one per rule).
  - `node scripts/check-a11y.mjs` — the accessibility contract, with no baseline because every rule is absolute: nothing in `src/` writes an inline `outline` (it outranks the engine's ring — that is how a focused field came to have none) and the registry routes no `outline` prop; `src/utils/focusRing.js` still holds the `:focus-visible` rule, the `--color-focusRing` token and the `[data-fb-field]` `:has()` pair, injected once from `createWidget.js`; both palettes define `focusRing` and the rule's boot fallback equals the boot palette; `effects.js` still gives a pressable widget role, Tab stop, Enter/Space and a released keydown listener, and does it outside the `disableTransform` branch; every file that reads the Escape key also imports and releases `trapFocus`; the trap's `FOCUSABLE_SELECTOR` and the ring's selector are the same list; no widget or navigation assigns `el.onclick` after the factory returned unless the same file passes it to `applyEffects` (the Dropdown's listbox option is the one allowlisted exception, and a stale entry fails too); and `Input` still writes the field marker. Proven by 19 mutations, one per guard.
  - `node scripts/check-error-boundary.mjs` — the contract for the error boundary (`src/utils/errorBoundary.js`), thirteen rules with no baseline: the two window listeners exist, the engine installs the boundary from `createWidget.js`, the factory catches a build **and** an update throw (and an update that throws keeps the content the widget had), `runApp` catches a throw in the component body, every handler is attached through `guardHandler`, the placeholder speaks with the DOM instead of markup, paints with theme tokens and framework units, is announced (`role="alert"`), and the marker is the exported constant rather than a literal. The module must still import in Node. Proven by 13 mutations, one per rule, and the browser harness (`tests/errorboundary.html`) proves the behaviour at runtime.
  - `node scripts/check-prop-registry.mjs` — the `ALL_PROPS` registry vs what widgets/navigations actually read.
  - `node scripts/check-docs-props.mjs` — the `docs/widget/*.md` prop tables vs the registry, the implementations and `src/index.d.ts`. Blocks `DEAD` (a documented prop nothing routes or reads) and `BOOL_STYLE` (a documented `boolean` that reaches CSS as `1` because its registry entry has no `boolValues`).
  - `node scripts/check-api-contract.mjs` — the contract for the API surface: the four disagreements between the four places a prop lives (the barrel, the engine's registry, `src/index.d.ts` and the widget's own source). It builds a **fixture package** in a temp directory — a real barrel, a real `index.d.ts`, real widgets — carrying one prop of each kind, and `unpackWidget` must report exactly those: `DEAD` (declared, routed by nothing, read by nothing), `INVENTED` (read by the widget, declared nowhere), `UNDOCUMENTED` (the engine routes it, the interface hides it) and `DOC-ONLY` (the doc page promises it, the code has never heard of it); a widget whose four surfaces agree must report none. On the real framework the first three are **absolute** — they are at zero, and a zero that grows is a defect, not debt — while `UNDOCUMENTED` is pinned by `scripts/api-contract-baseline.json`, which may only shrink and is **empty today** — the 22 props that used to live there (`boxSizing`, `flexDirection`, `flexGrow`, `flexShrink`, `paddingTop/Left/Right/Bottom`, `gap`, `fontSize`, `icon`, `thumbColor`, `borderColor`, `borderWidth`, `dividerColor`) are declared in `src/index.d.ts` now, because each one was a call the editor underlined for being right. `--write-baseline` regenerates it, and only after a fix. A fifth code, **OPTIONAL-CALL**, is not a disagreement between surfaces but a promise one of them breaks: the interface says an argument may be omitted (`props?:`, `width?: number`) while the implementation has no default for it, so the call that the type allows arrives as `undefined` in a way the code never decided — `ThemePicker` was declared `props?:` and destructured its argument unguarded, and `border()` was declared with an optional colour and had none. It is scoped to the **widgets** (a capitalised export), because a lowercase utility deliberately decides what `undefined` means inside its body: `join` lets `Array.prototype.join` pick the separator, `stopAnimation` reads `undefined` as "every animation". Every widget the interface declares optional must be callable with no arguments — and `tests/widget-smoke.test.js` proves the same thing at runtime, by calling each of them with no arguments.
  - `node scripts/check-api-surface.mjs` — API coupling across the three surfaces. It imports `src/index.js` for real, so it also fails when the barrel re-exports a name that no longer exists, or when the package stops being importable in Node (module-scope `window`/`document`).
  - `node scripts/check-bundle-size.mjs` — the **budget for what FletBox weighs**. It builds two entries with the same esbuild options `createBundle` uses (and reads `bin/commands/createBundle.js` to prove the two have not drifted apart, because a budget that measures a different bundle than the one that ships is blind): `framework`, the whole public surface imported wholesale (`import * as FB from "flet-box"`, 351 KB raw / 111 KB gzip today), and `demo`, this repository's own app (`src/app.js`, 82 KB / 22 KB). The ceilings live in `scripts/bundle-budget.json` together with the per-module ledger, so a growth is not just "the bundle grew" but "and `src/widgets/Text.js` grew 85 B". Growth is allowed but only by an act of acceptance — `--write-baseline` regenerates the file and the diff is the receipt; a run that came in *under* the ceiling says so, because lowering it is the point of keeping one. The **raw** size is the hard ceiling (it is esbuild's own output and is byte-identical on every machine); `gzip` and `brotli` carry a 1% tolerance, because zlib's output changed between releases (this checkout runs Node 26 with zlib 1.2.12, CI runs Node 22 with zlib 1.3) and the transported size is a range, not a number two machines can agree on. esbuild is a devDependency, so the script skips with a notice when it is absent.
  - `node scripts/check-api-propscan.mjs` — the contract for the prop scan of `flet-box check-api`: the keys of a widget's props object are read at that object's own level and nothing else. The scanner used to split a props literal on every comma it found inside the braces, so a child list — `children: [slot, line]`, the most common shape in an app — was read as shorthand props (`Column({ line })`, UNKNOWN_PROP, exit 1). Both directions are asserted: the false positive must stay gone **and** a real invented prop must still be reported, or the guard would pass by disabling the check.
  - `node scripts/check-time-helpers.mjs` — the contract for the time and string helpers `flet-box` exports: every named export of `src/tools/time.js` and `src/tools/string.js` has to be a function on the public barrel (43 of the 47 time helpers and 6 of the 12 string helpers stayed private, so an agent following the "use a tool, not boilerplate" rule reached for the language instead), and each helper has to keep its behaviour.
  - `node scripts/check-router-base.mjs` — deployment base path.
  - `node scripts/check-clean-ui.mjs` — the contract for `flet-box check-ui`: the screen the design skill recommends must produce **no** finding, and every tier must be proven to bite by breaking it. Its last two sections are about who may decide: `verify` counts a finding the framework wrote down in `framework-ui-baseline.json` as accepted (a code that is an error elsewhere included, which is what the reason is for) and still reports the same finding inside an app, whose baseline the gate never reads. And the two themes must expose the same token names — the light palette once answered five fewer tints than the dark one and the boot palette, so `setTheme("light")` deleted `colors.errorBg` & friends out from under an app that was already writing them.
  - `node scripts/check-framework-ui.mjs` — the same gate, run on this repo's `src/`: `npm test` fails when a default the framework ships breaks a rule it teaches. `scripts/framework-ui-baseline.json` is shrink-only and every entry carries its reason; `--write-baseline` exits 1 while an entry has no justification, so a new finding is fixed rather than snapshotted.
  - `node scripts/check-structure.mjs` + `node scripts/check-ui-rules.mjs` — the acceptance tests of the structural gate and of the design rules: each rule is proven twice, once by breaking it and once by obeying it, and the clean project must produce no finding. The second one delegates to the gate that owns each rule rather than re-implementing it, so a rule cannot drift away from the checker that enforces it.
  - `node scripts/check-syntax.mjs` — the contract for the two gates `verify` gained. The parse half: a fixture with an unclosed call must be reported at its line and column with a caret and a hint, a clean project must report nothing, and a broken file inside `node_modules`/`www`/`dist` must not be parsed. The suite half: a failing `test` script must reach the finding with its own words and no npm noise, a green one must pass, a project with no script must be skipped rather than failed, and a `verify` inside a `verify` must not run the suites again. Both directions are asserted — the silent version of each gate is exactly what shipped before the contract existed.
  - `node scripts/check-metrics.mjs` — the contract of the metrics log and the north metric (`bin/commands/metrics.js`): the arithmetic of a generation is proven with a fixture, a code that recurs three times with no rule behind it must fail the command, and every code in this repository's own log must have an owner.
  - `node scripts/check-skills.mjs` — the `skills/` folder contract (see Skills below): each file loads, every API it teaches is real (fenced blocks through `checkApi`, inline `Widget({ prop: … })` through `bin/utils/dtsProps.js`, and every one of those calls against `src/widget-factory/deprecations.js` so a skill cannot teach a prop the framework has renamed — `Switch({ onToggle })` outlived its own migration that way — every `colors.X` against **both** palettes, every effect against `AnimatedBox`, every rule number against the codes `checkUi` reports), the folder is in the tarball, and a freshly created app gets byte-identical copies in all three loader roots with every markdown link resolving. Both halves are mutation-tested: an invented prop and a pointer at nothing must fail the script.
  - `node scripts/check-app-types.mjs` — the generated app's editor contract: `flet-box create` writes a `jsconfig.json` (`allowJs` + `checkJs`, `moduleResolution: bundler`, `strict: false`) so the editor's own JavaScript language service reads `src/index.d.ts` — every widget and prop autocompletes and an invented prop is underlined, with nothing installed and nothing compiled. The script creates all five templates, symlinks this checkout into each `node_modules`, and requires **zero** TypeScript diagnostics over `src/`; then it injects one invented prop and fails if the checker stops catching it. Needs `typescript` (a devDependency — never shipped) and skips with a notice when it is absent. TypeScript 7 removed `moduleResolution: node10`, which is why the config says `bundler`. It caught seventeen real declaration bugs on its first run (`maxWidth`/`flex`/`marginTop`/`border*` missing from `CommonProps`, `Chip.size` typed as a preset when it is a pixel size, `Scaffold` slots typed `Widget` when the engine calls factories, `Divider()` requiring an argument) — when it fails, fix the `.d.ts` or the template, never the jsconfig's `checkJs`.
  - `node scripts/check-codegen-contract.mjs` — the contract for `AGENTS_FOR_CODE_GEN.md`, the file that tells an agent which widgets exist, what it may write and how its work is proved: it ships inside every app `flet-box create` builds, and it is the **entry point** for an agent that has never seen the framework, so a wrong name there is worse than a wrong name in a comment. Every good example must pass the anti-hallucination gate, every bad example must be rejected by it, every inline `Widget({ prop: … })` must name a real widget and prop, every `colors.X` must exist in **both** palettes, every rule number it cites must exist in the design skill, every command it names must be a real one, and `flet-box create` must hand the app the contract byte for byte. It also checks the app's own `AGENTS.md`: a sentence that introduces a list of props is a claim about the API, and the factory drops a key it does not know — the contract taught `radius` for years while the registry calls it `borderRadius`, so every screen that copied the line had a silent no-op. The guard reads the generated app's own file, so a template that teaches a prop nothing declares fails the build.
  - `node scripts/check-migrations.mjs` — the contract for the migration guide (`docs/guides/migration.md`, Chapter 14) and the codemod that applies it. One table is the source of truth for every rename: `src/widget-factory/deprecations.js`. The guide's "de X a Y" rows, the `@deprecated` markers in `src/index.d.ts`, that table and `flet-box audit-fix --only migrations` must all name the same things — a prop deprecated in the types but missing from the guide fails CI, not the user's app. The script proves both directions (a row without a deprecated marker fails, a marker without a row fails), that every target is a prop the widget really has, that the codemod renames what the table says and leaves a call that already carries the new name alone, and that `flet-box release --major` refuses to publish without a section for the version it publishes. The guard only fires in the framework repository (`isFrameworkProject`), never in a consumer's app.
  - `node scripts/check-ota-assets.mjs` — the guard for OTA releases that ship more than the JS bundle: the manifest must name each extra file with a hash and a size, and the loader must publish the helper that reads them. A manifest that described exactly one artifact let an installed app update its code while every other file stayed frozen at the version its APK/IPA was built from — the visible symptom was a catalog listing a page the device did not have. It also holds both share cards to the same list: the template `flet-box create` ships and this repository's own root `index.html` (what `npm run build` and `flet-box cloudflare` serve) must each carry every tag in `SHARE_TAGS`, declare `twitter:card`, name a picture that exists, and stamp absolute in the built copy — the demo shipped a headline with no picture for exactly as long as nothing checked it.
  - `node scripts/check-pwa-shell.mjs` — the guard for the two defects that made a deployed FletBox PWA look broken while the app itself was healthy: GitHub Pages answers an unknown path with a real 404 *response*, and the service worker's shell fallback used to live only in the `catch`, which a response never reaches, so the host's error page was handed to the browser; and the shell the worker served was not the app's own `index.html`. The worker is run against a fake 404 network, so the navigate case is proven to answer with the shell and not with the host's page.
  - `node scripts/check-cli-install.mjs` — the shape of the **published** package: it `npm pack`s the repo, extracts the tarball and runs `bin/cli.js` from it with no `node_modules` in scope, which is the only place where a `bin/` module reaching for a devDependency at import time shows up (it used to break every CLI command for consumers, since the checkout always has `ws`/`chokidar`). It also asserts `docs/widget/` shipped.
  - `python3 tools/snippets-creator-flet-box/build_snippets.py --check` + `node scripts/check-snippets.mjs` — the VSCode snippet library (see Snippets below). Every tier of the checker fails the build, `BROKEN_CALL` included: a body is pasted without being read, so a call to a name neither the package nor the body declares throws in the reader's file.
  Behavioral tests are browser harnesses in `tests/` (below).
- `python3 scripts/generate_widget_docs.py` — regenerates `docs/widget/*.md` from `src/index.d.ts` + the curated examples in `scripts/_docdata/`. Run after changing a widget's public props/types. Every page is generated, prose included, so `docs/widget/` is never hand-edited: an edit is lost on the next run — write it in `_docdata` and regenerate. `--check` (in `npm test`) compares the tables **and** the prose of all 57 pages against the render and names the ones that drifted, in either direction, which is what keeps a hand edit from quietly living in only one of the two places; `--tables-only` refreshes just the tables and leaves every other line byte for byte. Prop blurbs live in the flat `DESC` map, which is keyed by prop name **alone** — adding `markers` there for one widget rewrites every page that documents a `markers` prop. When a name already means something else elsewhere (`markers` = pins on a map, ticks on an arc), put the blurb in `WIDGET_DESC[Widget][prop]` instead.
- Snippets: the dictionaries in `tools/snippets-creator-flet-box/FletBox_snippets_creator/` are the ONLY source. The four JSON files beside them (including the aggregate `FletBox.json`, which is what the editor loads) are build output — never hand-edit them, run `python3 tools/snippets-creator-flet-box/build_snippets.py`. Prefixes must stay unique across the three dictionaries: one prefix, one snippet, or the aggregate silently keeps the first file's version. Every body declares what it calls: a placeholder **handler** logs what it represents (`onPress: () => console.log("submit")`), a placeholder **screen** is a real widget (`Column({ children: [Text({ text: "Home" })] })`, not `HomeScreen()`), and a body that needs a helper declares it above itself (`const Header = () => Text(…)`, as `Column.full` does). A parameter is a binding, so `(item) => …` and `({ onSelect }) => onSelect(item)` are not findings — but a free call to anything else fails `npm test`, because a snippet exists to be pasted and a name nobody declares throws on the first frame.
- `flet-box build android [--release [--aab]]` / `flet-box build ios [--archive]` — Capacitor builds, run **inside a generated project**. Both share `bin/utils/capacitor.js`; each owns its toolchain checks (`buildAndroid.js`: SDK + JDK; `buildIOS.js`: full Xcode + CocoaPods + simulator runtimes). Android `--release` leaves the artifact **unsigned on purpose** so it can be signed with the developer's own keystore (`apksigner` for the APK, `jarsigner`/Play App Signing for the AAB).
- `flet-box run-native <android|ios> [--device|--livereload]` — wraps `npx cap run` to compile and launch on an emulator/simulator or device. It reuses the toolchain helpers exported by `buildAndroid.js` (`prepareAndroidEnvironment`) and `buildIOS.js` (`requireAppleToolchain`); keep those exports when editing the build commands.
- No lint/formatter/typecheck config exists. Validate JS with `node --check <file>` and `python3 -m py_compile scripts/generate_widget_docs.py`.
- `flet-box audit-fix` (aliases `fix-imports`, `fix-path-imports`, `auditFix`) is the *repair* half of that gate: it rewrites what `check-api` can prove — a wrong relative path, a default import of a named-only widget, a missing `import` line for a bare identifier (merged into the existing flet-box import when there is one), and a mistyped prop key — and prints everything ambiguous under "Left for you to decide" untouched. `--only imports|props|migrations`, `--root <dir>`. It writes files directly, so the rule is strict: rewrite only when **exactly one** candidate is within a length-gated edit distance (`strictMatch` in `bin/commands/auditFix.js`: 0 for names < 4 chars, 1 up to 8, 2 from 9) and a tie means no edit. Prop keys are only touched when the identifier is a known flet-box import and the key is in neither `PROP_MAP` nor `STRUCTURAL_PROPS`. `flet-box create` wires it as `npm run fix`. Reuses `loadApi`/`nearest`/`collectSources`/`STRUCTURAL_PROPS` exported from `checkApi.js` — keep those exports.
- `--only migrations` is the third repair, and it is the one that writes the guide's table: it renames a deprecated prop inside a widget call when the widget declares both names and the call does not already carry the new one, and it removes a key the table marks as removed. The renames come from `src/widget-factory/deprecations.js` — the same bytes the guide, the release guard and `scripts/check-migrations.mjs` read — so a new deprecation is one row, not four places.
- `flet-box check-api` (alias `flet-box check`) is the anti-hallucination gate: it imports `src/index.js` and reads `translateProps.js` + `src/index.d.ts` of the resolved package and reports invented widgets/props, positional widget calls, foreign-framework imports and broken imports between the app's own modules (`MODULE_NOT_FOUND`, `MISSING_EXPORT` — a name the target file never exports, resolved statically so it works offline and in CI). `--props <Widget>`, `--list`, `--emit-api`, `--json`, `--root <dir>`. Errors exit 1. `--emit-api` writes the cheatsheet an app's agent reads first, and it marks a renamed prop `(deprecated → x)` — an unmarked `onToggle` beside `onPress` reads as a second spelling instead of the one being retired. `flet-box create` wires it into every app as `npm run check` (plus `AGENTS.md`, `.claude/CLAUDE.md`, `.cursor/rules/fletbox.mdc`, `.fletbox/memory/` and `.fletbox/api/cheatsheet.md`), and CI runs it — so a template that uses a non-existent export or prop fails the generated app immediately.
- `flet-box unpack <Widget>` (`bin/commands/unpack.js`) is the *read* half: it cross-checks the four places a prop lives — `src/index.d.ts`, the `ALL_PROPS` registry, the widget's own source, its doc page — and labels every disagreement `DEAD` (typed, routed by nothing, read by nothing), `INVENTED` (read by the widget, declared nowhere), `UNDOCUMENTED` (the engine routes it, the interface hides it), `DOC-ONLY`, `CODE-ONLY`. Flags: `--example` (a paste-ready call built only from verified props, never carrying a renamed one, sampling no blind `width`/`height` — a number pasted into `Switch` collapses it — and never dropping a required one), `--diff`, `--all`, `--json`, `--md`, `--root <dir>`. `unpack --all` writes `.fletbox/api/api.json` + `api.md`; `flet-box create` generates them at scaffold time and wires `npm run api` to regenerate. Two invariants to keep: the widget filter is `exported && propsSource()` (a singleton API like `initRouter` has no props interface and must not appear), and `readProps()` reads structure from the **neutralised** source (`bin/utils/neutralise.js`) while slicing values out of the raw text at the same offsets — splitting a destructuring pattern on raw commas invents props, which is exactly how `Consolas/Menlo/Monaco` became props of `Markdown`. Shared parsing lives in `bin/utils/dtsProps.js` (`parseSignatures`, `membersOf`, `resolveInterfaceProps`) and is reused by `check-api`; keep those exports and `loadApi`/`nearest`/`STRUCTURAL_PROPS` in `checkApi.js`.
- `flet-box to-png [dir]` (aliases `topng`, `convert-images`; `bin/commands/toPng.js` + `bin/utils/images/`) converts a folder of asset images to PNG with **Node core only** — no `sharp`, no CLI binary. The decoders are the point: JPEG (baseline + extended sequential, grey/RGB, any sampling factor, restart intervals), PNG (colour types 0/2/3/4/6, 1–16 bit, all five row filters, `tRNS`), BMP (uncompressed 1/4/8/24/32) and GIF (first frame, interlace, transparency). Progressive JPEG, Adam7 PNG, RLE BMP, WebP, AVIF, TIFF, ICO and SVG are **declined by name**, never guessed. Format comes from the bytes, so a `.jpg` that is really a PNG is read as a PNG — keep it that way. The writer is the other half: `encodePng` picks the layout from the pixels it is handed (an exact palette when there really are ≤256 distinct colours, grey when the channels already agree, three bytes per pixel when no pixel uses alpha) and picks row filters by deflating the candidates at level 9 and keeping the shortest IDAT, so the output is the smallest **lossless** PNG it can find — nothing quantises a pixel, and `FULL_SEARCH_LIMIT` is what stops a 2738² photo from searching six deflates per layout. It is non-destructive: the source stays, `logo.png` is written beside it, and an existing `logo.png` is reported as a name clash instead of overwriting a hand-made asset (`--force` opts in); `--replace` deletes a source only after the written PNG has been read back (`writtenPngMatches`). `--optimize` re-packs files that already are PNG and replaces one only when the new bytes are smaller **and** `pngHoldsThePicture` reads them back equal, through a temp file plus a rename; a 16-bit PNG is left alone, because narrowing it is losing quality for a byte count. A photograph's PNG is 3–4× its JPEG and that is the format speaking — the command converts anyway and prints the ratio, so do not "fix" it by refusing. Flags: `--out --replace --force --optimize --flat --dry-run --quiet`; the summary counts converted / declined / already png / optimized / already optimal / name clash and the bytes saved, and only an undecodable file counts as a failure (exit 1). Contract: `node scripts/check-image-convert.mjs` (in `npm test`, and it needs nothing but Node: the fixtures are tracked) compares the decoders against `tests/fixtures/images.json`, whose expected pixels come from another decoder, not this repo's: lossless formats must match byte for byte, JPEG is measured against libjpeg's own pixels (mean ≤ 0.33, worst channel 2 — the line printed per fixture is the regression signal). The optimizer asserts on the same fixtures: never bigger than the plain type-6/None writer, never type 6 for an opaque frame, never a palette over 256 colours, and `every layout is reached` (types 0/2/3/6) so a branch cannot go untested because no fixture hits it — `png-gradient` (1024 colours) exists for exactly that. Every one of those guards has been proven to bite by mutating the rule in a scratch copy; a new one needs the same, and note that a mutation only counts if it changes the layout the picker *selects* (a size-neutral corruption), or the search silently routes around it. Regenerate fixtures with `python3 scripts/generate-image-fixtures.py`, which needs **Pillow and is dev-only** — like `tests/` itself it sits outside `package.json` `files`, so neither the generator nor the fixtures reach a consumer. `scripts/check-cli-install.mjs` is what proves the whole thing survives `npm pack`: no `bin/` image module may import anything outside `node:*`.

- `flet-box images [dir]` (aliases `optimize-images`, `imgs`; `bin/commands/images.js` + `bin/utils/imageTools.js`) is the **lossy** half, and it delegates: a photograph has no answer inside `dependencies: {}`, so the command finds the platform's own encoder (`cwebp`, then `magick`, then `convert`), probes it with `--version` rather than `which`, and shells out to it — the same shape as `runCloudflare.js` requiring `cloudflared` and `buildAndroid.js` requiring the SDK. A binary is not an npm dependency and no `bin/` module here imports anything outside `node:*`, which is what `check-cli-install.mjs` keeps proving. When nothing is installed it prints the one command for that machine (`platformInstaller()` reads `process.platform`, and on Linux the family from `/etc/os-release`, because apt/dnf/pacman are different sentences); `--install` runs it, and only on a TTY — a CI runner must not find a CLI reaching for `sudo`. The search order is the contract: pixels first, quality second (`WIDTH_SCALES` then the quality ladder down to `QUALITY_FLOOR = 62`), because a soft 540px q70 photo beats a blocky q44 one and nothing on a page renders the pixels a 2000px sensor captured. Non-destructive like `to-png`: the WebP is written beside the source, an existing one is a name clash unless `--force`, a WebP already inside the budget is **not** re-encoded (a second lossy pass on bytes the same encoder already chose buys nothing), and `--replace` deletes a master only after the output's 12 header bytes sniff as `RIFF…WEBP` — there is no WebP decoder here, so that is the honest read-back. Flags: `--budget <KB>` (40), `--width <px>`, `--quality <n>`, `--force --replace --install --dry-run --quiet`; only an encoder that produced nothing counts as a failure (exit 1), and a file that cannot fit the budget is still written at its smallest attempt and printed `OVER`.
- `flet-box prune-assets [dir]` (alias `prune`; `bin/commands/pruneAssets.js`) deletes the images a generated app never names, because `flet-box create` ships a demo library (dishes, drinks, gallery) that no screen imports and that any broad asset glob drags into a release. A file is referenced when its path **or** its exact filename appears in `src/`, `index.html`, `scripts/`, `fletbox.config.json`, `package.json`, `README.md`, `AGENTS.md` — with comments stripped first (`mojito.jpg is the frappé` is documentation, not a load) and `www/` excluded, since a name that only appears in generated output is a stale bundle, not a consumer. `assets/logo.png` is protected by rule: the native icon and splash scripts build that path at runtime, so a text scan cannot see its consumer. Dry run by default, `--apply` deletes, `--keep <name>` adds a protection, and it refuses a folder outside `--root`. The asset dir resolves against `--root`, never against the shell's cwd — that disagreement is exactly what the first draft of `scripts/check-images-cli.mjs` caught.
- `node scripts/check-images-cli.mjs` is the contract for both, and it runs in `npm test`. Its fixtures are **synthetic**, written by the repo's own `encodePng`, so no Pillow and no committed bytes are involved. The `images` checks shell out to a WebP encoder, so they print a skip when cwebp, magick and convert are all absent — a host that cannot run the command must not fail the gate — while the platform table and the whole `prune-assets` contract always run.
- `images --referenced` publishes only what the app actually loads, and it is stricter than "the name appears somewhere": a WebP is written when the app names **the WebP**, never because it names the source it would replace. That is what kept `favicon.png` — a format the browser must be handed as PNG — from being converted into a file no consumer asks for. `--replace` refuses to delete a master the app still names in its own extension (`source kept: the app names X.png, not X.webp`).
- Alpha is verified from the written bytes, not from the encoder's exit code. `hasTransparency()` reads the decoded source, `webpCarriesAlpha()` reads the RIFF chunks back (`ALPH`, then the `VP8X` flag bit, then the `VP8L` packed word), and a WebP that lost the transparency is deleted and the file printed as failed. A lossy encoder quietly dropping a transparent margin is exactly what "the icon turned white on every home screen" would have been, and the negative control in `check-images-cli.mjs` asserts an opaque source is reported opaque, so the guard cannot pass by always saying "alpha".
- `decodeImage` declines WebP and progressive JPEG; `readImageHeader()` still reads **size and alpha presence** from those headers (`SOF` markers, `0xC4`/`0xC8` skipped, `0xC2` noted as progressive). An `UnsupportedImage` is therefore not a dead end for `images`: the encoder reads the file itself, the header only picks the scale ladder. It is what let `og-cover.jpg` be shrunk instead of skipped.
- `createBundle` stamps the social preview card: `absoluteShareTags()` (`bin/utils/bundleConfig.js`) rewrites the four tags in `SHARE_TAGS` — `og:image`, `og:url`, `twitter:image`, `twitter:url` — to absolute URLs from the OTA origin, and `www/index.html` is the only file it touches. It prefixes values with no scheme, so it is idempotent, and leaves every other meta alone. The template every generated app's `index.html` comes from (`indexHtml()` in `bin/utils/templates.js`) carries all four plus `twitter:card`, the titles and descriptions, pointing at `./src/assets/icon-512.png` — a file `flet-box create` copies and `createBundle` puts at the same path in the bundle, so it resolves on `:8000` *and* on Pages. A stamper with nothing to stamp is the failure mode this pairing closes: the app looked perfect and every share was a headline with no picture. `check-ota-assets.mjs` holds the template to the stamper's own `SHARE_TAGS` list, so adding a tag to one without the other fails `npm test`. A share scraper crawls from `https://`, not from the repo's `<base>`: without this the link preview shows no picture at all, even though the page itself is fine. Guarded by `check-ota-assets.mjs`.
- A Pages deployment is built from the **published npm package**, not this checkout, so what `createBundle` copies on this machine is not proof of what CI publishes. `githubWorkflow()` is the only workflow shape a generated app gets (`concurrency: group pages / cancel-in-progress: false`, `actions/configure-pages@v5` in the build job, `upload-pages-artifact` with `path: www`, `deploy` needing `build`) and `check-router-base.mjs` asserts that shape over the generated text — a `tags:` key that drifts out from under `push:` makes the whole file unparseable, and GitHub then reports a failed run with no job and no step to read.

- The generated app's agent contract is `templates.agentsMd()` in `bin/utils/templates.js`, mirrored by `claudeMd()` and `cursorRules()` — all three are arrays of single-quoted lines joined with `\n`, so an apostrophe inside a line must be escaped or the template stops compiling. Its numbered sections are load-bearing and cross-referenced by number ("the design system in section 4", "the checker in section 5"): inserting or removing a section means renumbering the rest and that prose. §4 is the design system (one brand color per screen from the `colors` tokens, no hex literals; spacing/radius/type only from the 8-based scale 4·8·12·16·18·24·32·48) and every token name in it was read off the real `colors` export — do not "tidy" one into a name that does not exist.
- `flet-box create <name> --template <basic|adaptive|blank|full|sidebar>` (and `--template=<name>`) is equivalent to the `--blank`-style flags. The **first** positional is always the project name; a later one is treated as an unclaimed flag value and is ignored, because a value that leaked past the parser used to rename the project (`create myapp --template blank` built a folder called `blank`).

## Skills

`skills/` at the repo root is the framework's knowledge of how to build and design
a FletBox app, written as four real markdown files — one per subject, not one per
idea:

- `fletbox-rules` — the working contract: FletBox syntax only, never invent an
  API (and the four ways to look one up), the rem rule, aliases, cleanup, the two
  gates, the memory duty.
- `fletbox-design` — the numbered design rules (00…24). Every code `flet-box
  check-ui` reports maps to one of them, and `docs/guides/clean-ui.md` keeps the
  code→rule table, so renumbering a rule means editing that table in the same
  change; `scripts/check-skills.mjs` already fails if a code the gate emits is not
  named by the skill.
- `fletbox-motion` — whether a thing may move, and through which of `AnimatedBox`,
  `AnimatedText`, `ParallaxBox` or `animate`.
- `fletbox-memory` — the `.fletbox/memory/` journal that hands progress from one
  AI to the next, including `notes/current-status.md`.

`bin/utils/skills.js` reads them (`skillRoot`/`skillNames`/`readSkill`/
`readFrontmatter`) and `flet-box create` **copies the bytes** into the app at
`skills/`, `.claude/skills/<name>/` and `.qoder/skills/<name>/` — the last two are
where those assistants load a skill from, so they are mirrors, never the source —
plus a `.cursor/rules/<name>.mdc` pointer per skill (`templates.skillCursorRule`;
`fletbox-rules` and `fletbox-design` are `alwaysApply: true`, the other two fire on
their subject). Keep `package.json` `files` carrying `skills/` or an installed app
has no design contract at all. `scripts/check-skills.mjs` proves the whole chain.

Do not add a fifth skill for one new idea — extend the file that owns the subject,
and move anything the four already cover out of `templates.js` prose. The set is
four on purpose: an agent that is sent to nine files reads none.

Those four are **app** guidance. The playbooks that audit this framework live in
`.qoder/skills/` instead — `fletbox-api-coherence-audit`, `fletbox-examples-app-verify`,
`fletbox-shared-helper-extraction`, `fletbox-snippet-library-audit`,
`fletbox-widget-default-verification` and `fletbox-widget-default-visual-audit`. They
are maintenance, not scaffolding: `flet-box create` never copies them, and they are
project-scoped so they load only while working in this checkout. Each is a `SKILL.md`
plus its own scripts, and none of them depends on a sibling app — a probe resolves the
checkout it audits from `--root`/`FLETBOX_ROOT`, never from a hardcoded path.

## Generated mobile projects

`flet-box create` writes the Capacitor scaffolding: `capacitor.config.json`, `assets/logo.png`, and one asset script per platform (`scripts/sync-android-icons.mjs`, `scripts/sync-ios-assets.mjs`) wired into the `android:sync` / `ios:sync` npm scripts. Every template is a string in `bin/utils/templates.js` **except** the skills, which are files in `skills/` precisely so the prose has one copy.

Quirks that are easy to break when editing those templates:

- A template literal cannot contain unescaped inner backticks in the generated file. Inside a generated template literal, a nested backtick must be `\\\`` (emits ``\` ``), and a nested `${` must be `\\${`. When in doubt, generate the project and `node --check` the output.
- The iOS asset script reads icon/launch slots from `ios/App/App/Assets.xcassets/*/Contents.json` instead of hardcoding file names, because Capacitor owns those names and can change them between major versions.
- The iOS app icon must be flattened onto an opaque background: App Store validation rejects icons with an alpha channel.
- `LaunchScreen.storyboard` lays the splash image out inside the safe area, so its background color must match the launch image or the notch strip flashes white.


## Testing

Tests are dependency-free JS in `tests/`. They can be run headlessly with `npm run test:browser` (`scripts/run-browser-tests.mjs`: serves the repo, drives the system Chrome through puppeteer, and reads each harness's global). That script is optional — it resolves puppeteer from `$FLETBOX_PUPPETEER` or a sibling checkout and a browser from `$FLETBOX_CHROME` or the usual install paths, and skips with a notice when either is missing, so it never breaks `npm test`. To run one harness interactively: `npm run dev`, then open:

- `/tests/index.html` — widget-factory regression contract. Treats the factory as frozen: fixes belong in widgets, not `src/widget-factory/`.
- `/tests/smoke.html` — instantiates every widget to catch `ReferenceError`s.
- `/tests/motion.html` — the motion contract: the named transitions actually move the element (`translateX/Y`/`rotate`/`scale` merge into one `transform`), every `EASING_NAMES` curve starts at 0 and ends at 1, a spring settles, and reduced motion (`setMotionMode('reduce')`) collapses every loop to one frame that writes the end value.
- `/tests/a11y.html` — the accessibility contract: a focused control paints the engine's ring (2px at 2px offset in `--color-focusRing`, and the harness re-registers that token to prove the ring reads it), `outline: none` appears on no element, a pressable `Container`/card answers Enter and Space, an icon wired after construction is a named control while a decorative one stays `aria-hidden` and off the Tab path, the three overlays trap the keyboard and give it back on close, and an invalid `Input` is `aria-invalid` with a live description that clears when the value becomes valid.
- `/tests/regression.html` — guards for the bugs fixed in the widget audit (engine child-wipe, `ListView.updateData`, `DataTable` body rebuild, `SnackBar.close` idempotency, `AnimatedBox` keyframe dedupe, `MatrixRain` loop teardown). Add an assertion here for every bug you fix: each one failed before its fix.
- `/tests/doccheck.html` and `/tests/doccheck-all.html` — assert documented behavior on the real runtime.
- `/tests/propscan.html` — prop scanner.
- `/tests/maps-chile.html` — manual Maps debug page: one map of Chile, no markers, with an on-page log of tiles loaded and the last `onMoveEnd`. Not an automated harness (no pass/fail globals); drive it with `window.__MAPS_DEBUG` (`{ map, stats, say }`).
- `/tests/md-visual.html` — manual Markdown page: headings, inline code, a fenced block with a line longer than the column, a table, a blockquote and a list, all on a white body. It is the only place the code block's horizontal scroll is read by eye — the visual baseline does not measure `Markdown` — so open it after touching the parser or `Markdown`'s styles. `window.__MD` is the widget.

Each harness writes a global (`window.__TESTS`, `window.__SMOKE`, `window.__REGRESSION`, `window.__DOCCHECK`, `window.__CONTRACT`, `window.__MOTION`, `window.__A11Y`) for automation. These pages cannot open via `file://` (ESM + CORS); they must be served.

### The visual baseline

`npm run test:visual` (`scripts/check-visual.mjs`) **measures** the gallery in both themes and compares the numbers with `scripts/visual-baseline.json`: 25 widgets × 2 themes, and for each one its colours, border, radius, type, padding, height, width and contrast. A token that moved, a radius that grew, a row that now wraps — none of that shows up in a type check or a prop contract, and a screenshot in git is a binary nobody can review in a diff.

What is compared, and how strictly: colours, border, radius, type and padding **exactly** (they come from the tokens, so two machines agree); the height with a 2 px tolerance; the width with a 1 px tolerance, and **only** for the widgets whose width the framework pins; the contrast with a 0.15 tolerance.

Three rules keep the measurement comparable between a laptop and the CI runner, and all three live in `tests/visual.html`:

- the root size is **pinned** (`html { font-size: 16px }`). Blink resolves the `medium` keyword against the font-family of each element, so an element that inherits its size takes the standard size of the font that happens to be installed — 13px for a monospace face, 16px for the system one. Without the pin, the inherited type follows the machine's fonts;
- the family is **pinned** to the metric-compatible pair Arial / Liberation Sans, and the line-height is a **unitless** number, so the line box is a pure function of the font-size. Measured across six unrelated families (monospace, serif, Times New Roman, Courier New, Verdana, Georgia) the fingerprint is **identical at zero tolerance**;
- the two measurements that belong to the font and not to the framework are **not compared**: `box: true` marks a widget whose width the framework pins (an icon, a switch, a code) and is left off the widgets that carry a label — `Checkbox` and `Radio` are as wide as their label — and `text: true` marks an **inline** root, whose height is the height of the glyphs. The type of an inline box is already compared exactly in `font`.

The browser is Chrome, driven over the DevTools protocol with `ws` — the driver the dev server already uses. No puppeteer, no downloaded browser: CI's runner already ships Chrome, and the script skips with a notice when no Chrome is found. When a change is intended, accept it with `node scripts/check-visual.mjs --write-baseline` — and only then: the baseline is a promise about how the framework paints, so it moves when the framework moves, never to make a gate quiet.

## Architecture

- Public entry `src/index.js`; types in `src/index.d.ts`. A public API is complete only when three surfaces agree: runtime implementation, `src/index.js` export, and `src/index.d.ts` declaration — `scripts/check-api-surface.mjs` enforces this under `npm test`. Two rules follow from it: every `interface`/`type` in `index.d.ts` must be `export`ed (otherwise consumers cannot `import type` it), and the package must stay importable in Node (never touch `window`/`document` at module scope — guard with `typeof window !== "undefined"`).
- `src/widget-factory/` is the ONLY rendering engine — `WidgetFactory` turns props into an `HTMLElement` with style, events, children, lifecycle, and reactivity. Never add a second rendering system.
- Adding a widget: file in `src/widgets/`, export from `src/widgets/index.js` and `src/index.js`, type + props in `src/index.d.ts`, doc page + `basic`/`normal`/`full` examples in `docs/widget/`.
- Prop aliases are a deliberate feature (e.g. `bgColor` ≡ `backgroundColor`, `onPress` ≡ `onClick`), resolved by the factory; each alias must keep exactly one meaning. Widgets also expose reactive property setters (e.g. `widget.text = ...`).
- State is key-based RAM + subscribers (`useState`); router lives in `src/navigations/Router.js`.
- Every length is a framework unit, not a pixel: a number on a rem-routed prop becomes `value / BASE_FONT_SIZE` rem, so the whole UI grows with the reader's browser font (that is what makes one build fit phone, tablet and desktop). `toREM` also rewrites a hand-written pixel shorthand — `"8px 12px"` → `"0.5rem 0.75rem"` — while anything that is not made only of pixel tokens (`"50%"`, `"calc(100% - 8px)"`, `"2px solid red"`) passes through untouched. Pixels stay where pixels are honest: canvas backing stores (QRCode, Chart, CircularBar, CircularChart), Maps' projected tile/pin space, values measured from the DOM (`offsetWidth`, `getBoundingClientRect`, scroll offsets), the hairline `borderWidth`, `SHADOW_LEVELS` depth, the focus ring's `2px` outline and `2px` offset (a visibility constant, not a length the layout scales — a rem would shrink it under the threshold that makes it visible), and a virtualised row's px-space math — `ListView` converts `itemSize + gap` through the live root font size so the slot a row gets scales the way the row's own box does. A device inset is the other honest exception: `env(safe-area-inset-*)` is unit-free to the scale gate (`UNIT_FREE` in `scripts/check-widget-scale.mjs`) because its `0px` is only the fallback for a browser that has no inset — that is how `AppBar` clears the status bar and `Drawer` its panel. The design numbers defaults are drawn from live in `src/tools/scale.js`, which `bin/commands/checkUi.js` re-exports so the app gate and the widgets cannot disagree.
- Widgets that register resources must clean them up: window/document listeners, timers/RAF, observers, router/storage subscriptions.
- Reduced motion is decided once, in the engine (`src/animations/motion.js`). `prefersReducedMotion()` is read by the imperative loop (`motionDuration()` collapses a run to one frame that writes the end value), by `AnimatedBox`, `ParallaxBox`, `MatrixRain` and `applyPulse`. Anything that ends up with an `infinite` CSS animation must carry the `data-fb-anim` hook so the once-injected `@media (prefers-reduced-motion: reduce)` rule reaches it: the factory's `setStyles` marks every `animation`/`animationIterationCount` write (that is what covers `Skeleton`'s wave and any app prop), and a widget that writes `el.style.animation` directly calls `markMotionLoop(el)` itself.
- Accessibility follows the same shape: decided once in the engine, never re-derived per widget. The focus ring is one `<style id="fletbox-focus-ring">` injected by `ensureFocusRing()` from `src/utils/focusRing.js`, called once in `createWidget.js`; it paints `:focus-visible` in `var(--color-focusRing, …)`, so a theme moves the ring with everything else. Nothing inside `src/` may write an inline `outline` — an inline value outranks the stylesheet and silently deletes the ring everywhere (`scripts/check-a11y.mjs` fails on the first one). The ring sits at `2px`/`2px` offset outside the border, so the border keeps reporting validation and the ring reports focus; a widget whose visual control is a wrapper around a native input marks that wrapper `data-fb-field` and the stylesheet rings the whole box instead of a hairline inside it. A press handler must arrive as a prop (`onClick`/`onPress`) at construction: `applyEffects` runs `makeKeyboardPressable`, which gives the element `role="button"` (only if it has none), `tabIndex=0`, Enter/Space, and releases its listener on unmount. Assigning `el.onclick` after the factory returned is mouse-only and caught by `check-a11y`'s `late-onclick` rule (the `Dropdown` listbox option is the one allowlisted case). The three overlays (`Modal`, `Drawer`, `BottomSheet`) hold the keyboard through `trapFocus` from `src/utils/focusScope.js` and release it on close, which returns focus to whatever opened them. A hover-only affordance is gated on `matchMedia("(hover: hover)")`: iOS answers the first tap with a synthetic `mouseenter` and never sends the matching `mouseleave`, so an ungated hover listener is a bubble nothing can dismiss (`Tooltip` does this, and keeps its `focus`/`blur` path open for everyone). Where a floating element must miss a viewport edge, `env()` has no JavaScript getter — measure it off an element that uses it: `Tooltip` reads the insets from a zero-size probe child of its own bubble, so showing a tooltip adds no second node to `document.body`, and it *flips* to the opposite side when the requested one has no room instead of clamping into the notch.
- The iOS text-field floor is the same shape, one layer down: focusing a control whose computed `font-size` is under `16px` makes WebKit zoom the whole page, so `src/utils/fieldFont.js` injects `html[data-fb-ios] [data-fb-field] input, textarea { font-size: max(16px, var(--fb-field-font, 1rem)) !important }` once, from `createWidget.js` beside the focus ring. It is a **floor**, not a size: `Input` publishes its own value as `--fb-field-font`, so a reader-raised root font still grows the field past 16px while the small preset stops shrinking it under the threshold. `!important` is required (the widget writes an inline font-size), the `html[data-fb-ios]` scope keeps every other platform pixel-identical, and `maximum-scale=1` is deliberately not used because it blocks pinch-to-zoom — `tests/regression.test.js` measures both halves (the computed floor and the untouched 14px elsewhere) and asserts the stylesheet is injected exactly once.

- A throw must never take the screen with it. `src/utils/errorBoundary.js` is that wall, in the three places a throw can escape. The factory (`WidgetFactory`) catches a throw while it builds a widget and the widget paints a placeholder **in its own place**, so the rest of the tree keeps working; a throw while it updates is caught too, and the widget keeps the content it had — `takePropChildren` returns the old nodes so the catch can put them back, because stale is not the same as empty. `runApp` catches a throw in the component body, which happens before any widget exists, and paints the root. `assignProps` wraps every handler in `guardHandler` where it is attached, so a throw inside an `onPress` is reported with the name of the widget that owns it instead of arriving as an anonymous stack. The engine installs the last wall itself — `installErrorBoundary()` from `createWidget.js` — for the errors no widget owns (a rejected promise, a timer that exploded): two window listeners, and `preventDefault()` is never called, because an error nobody can see is worse than a noisy console. The placeholder speaks with the DOM (never markup), paints with theme tokens (`var(--color-errorBg)` for the surface, `var(--color-text)` for the ink — the red is a rim, not a word), uses framework units through `toREM`, and is announced with `role="alert"`. The **host** carries the marker (`data-fb-error="<phase>"`), not the box, so one failure is one marked element. `scripts/check-error-boundary.mjs` is the gate: thirteen rules, each proven twice — once by breaking it in a copy of the source, once by obeying it on the real one — and `tests/errorboundary.html` proves the behaviour at runtime.

## Repo layout gotchas

- The backend is a separate package and repo, `flet-box-server` (a sibling checkout, `../flet-box-server`); `docs/server/` documents it from here. It is NOT part of this repo and is not published with the framework — don't wire it in, and don't import it from `src/`.
- `www/` and `dist/` are gitignored build output — regenerate them with `npm run build` or `flet-box release`, never hand-edit them. `www/` is built from the root demo (`src/app.js` + `index.html`) so `flet-box run-bundle` works here; in a generated app it is the OTA source that CI publishes to Pages — `build.yml` deploys every push (so the preview is never stale) but deletes `www/config.json` unless the ref is a `v*` tag, which is what keeps installed apps on the last release, and Android/iOS only run from `build-native.yml` when started by hand — and it stays out of git there too.
- `.github/workflows/npm-publish.yml` publishes to npm when `package.json` carries a version npm doesn't have yet; `.github/workflows/ci.yml` is the gate — it runs on every `pull_request` and on every push to `refactory`/`main`, and it publishes nothing (a pull request must never be able to reach `npm publish`, so the two workflows share nothing but the checkout). It runs `npm run verify -- --no-tests` (the unified gate, minus the suites, which have their own jobs) and `npm test` (the static checkers) in one job, the browser harnesses in another, and the **visual baseline** in a third: the runner already ships Chrome, so only the puppeteer driver is installed (`puppeteer@22`, the version the runner script's ESM import path matches, with `PUPPETEER_SKIP_DOWNLOAD` so a second browser is not fetched), and the visual job needs nothing but the Chrome the runner already has — the measurement is driven over the DevTools protocol with `ws`, which `npm ci` already brought. The three jobs run in parallel, so a broken measurement never hides a broken gate. The jobs stay separate because each names its own failure and a red measurement must not be able to hide a red check; `--no-tests` is what keeps each suite running exactly once, and it is a stated choice rather than the nested-run switch, whose "already inside a verify run" note is only true of a `test` script calling verify. APK/AAB CI belongs to generated apps (`bin/utils/templates.js` writes theirs), not here.
- npm ships all of `bin/`, so a stray `bin/package.json` would be published and shadow module resolution. Keep `bin/` free of package manifests.
- `bin/` may not import a devDependency at module scope. `ws` and `chokidar` exist only for the dev server, so `bin/cli.js` loads `runServer.js`/`runBundle.js`/`runCloudflare.js` with `await import()` inside their command branches; keep them lazy or `flet-box` crashes on every command for anyone who installs it from npm. `check-cli-install.mjs` (above) is the tripwire.

## Widget structure contract

Every widget follows the canonical, modular shape documented in
[`docs/guides/widget-structure.md`](docs/guides/widget-structure.md); `QRCode.js`
is the reference implementation. In short: one `WidgetFactory` root, `widgetName`
on that root, `composeUpdate()` instead of overwriting `container.update`, scoped
styles, and every resource released through an idempotent `onUnmount` disposer
(never `_cleanup` monkey-patching).

`npm test` enforces this statically via `scripts/check-widgets.mjs`; the debt
snapshot lives in `scripts/widget-contract-baseline.json` and must only shrink.
Before marking a widget done, also open `/tests/widget-contract.html` (runtime
contract) and `/tests/smoke.html` (every widget instantiates).

The second half of the shape is about what a widget does *not* own. A helper the
widgets share has one home in `src/helpers/` and every widget imports it —
`escapeHtml` in `src/helpers/html.js`, the four-side resolver behind
`margin()`/`padding()` in `src/helpers/boxEdges.js` — while the engine-owned ones
stay with their service: `injectKeyframes` and `animationName` in
`src/utils/styleInjector.js`, `toREM` in `src/utils/units.js`. A module in
`src/helpers/` imports nothing at all, which is why the escaper lives there and
not beside the Markdown parser: a widget can escape text without pulling six
widgets into its graph. `scripts/check-shared-helpers.mjs` is the gate: a second
copy, or a helper that grew an import, fails `npm test` and the message names the
home it belongs in. The rule is not tidiness — an escaper that exists three times
is a security boundary edited in one of them, and a keyframe injector per module
is a second dedupe set that cannot see the first.
